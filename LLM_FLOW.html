02

Chi tiết lệnh run

Các nhánh dưới đây phản ánh hàm reviews(), read_results(), run() và validate() trong src/llm.py.

1. Đọc dữ liệu và chọn mẫu — reviews(cfg)
Đọc CSV → lọc snapshot → kiểm tra trùng ID/listing → dùng đúng sample_ids → lấy văn bản + split
2. Tạo run_signature SHA-256
Hash base_url, model, prompt_version, request_options, PROMPT và ID/text/QA/split. API key và tên provider không nằm trong signature.
3. Kiểm tra --output
Có file: so signature, số dòng, bộ khóa review; không khớp → báo lỗi, không ép đọc. Chưa có file: tạo bản ghi mặc định error/not_attempted.
4. Duyệt lần lượt từng review
Quyết định theo trạng thái checkpoint, chế độ skip, giới hạn request và cờ QA.
TỪNG REVIEW → MỘT TRONG CÁC NHÁNH
A · Dùng lại checkpoint

Đã có ok / needs_review

Giữ nguyên bản ghi, tăng cache_hits. Không gọi HTTP; bản ghi hoàn tất không bị ghi đè bởi lần chạy sau.

B · Chưa gọi API

--skip-llm hoặc hết lượt gọi

Bản ghi còn error/not_attempted (hoặc trạng thái error cũ). Không gọi API. Nếu file chưa tồn tại mà dùng --skip-llm, chương trình báo lỗi.

C · Xét điều kiện gọi API

Review chưa hoàn tất

Nếu rỗng hoặc QA không đạt → error=input_failed_qa; nếu hợp lệ nhưng thiếu key → báo lỗi; nếu đủ điều kiện → gọi HTTP.

CHỈ NHÁNH C CÓ TEXT / QA HỢP LỆ + API KEY MỚI ĐI TIẾP ĐẾN HTTP. NHÁNH A/B BỎ QUA, ĐẾN BƯỚC 7.
5. Khi có HTTP request: POST /chat/completions
System PROMPT + user review · yêu cầu JSON · timeout từ config · không có vòng retry HTTP tự động.
THÀNH CÔNG

6a. Parse + validate

finish_reason = stop; JSON có đúng 5 trường; sentiment/aspects/language/status/error hợp lệ. Cập nhật bản ghi ok hoặc needs_review, lưu usage nếu API trả về.

Ghi toàn bộ JSONL checkpoint → in trạng thái → sleep theo cấu hình → review tiếp theo.

LỖI REQUEST / VALIDATION

6b. Dừng có checkpoint

HTTP 429/timeout/network, JSON lỗi, thiếu trường, finish_reason không đạt... → gán status=error, ghi file JSONL đầy đủ, in review lỗi và dừng batch.

Muốn thử lại phải chạy lại lệnh với cùng output/signature; chương trình không retry tự động ngay trong request đó.

7. JSONL kết quả + summary
rows · status_counts · cache_hits · api_requests_this_run — có bất kỳ error còn lại, run trả exit code 1.
File checkpoint là một snapshot đầy đủ của toàn bộ mẫu, không append từng review vào cuối file. Khi ghi, code dùng file .tmp rồi thay thế đích. Điều này giúp chạy tiếp, nhưng vẫn cần sao lưu dữ liệu cục bộ khi chuyển máy.

Hợp đồng dữ liệu LLM → KPI TV3

KPI của TV3 dùng JSONL TV4 theo các khóa và nhãn bên dưới. TV4 không tự tính lại KPI của TV3.

TrườngGiá trị / vai trò
snapshot_date
review_id		Khóa xác định review theo snapshot; không để trùng trong cùng một kết quả.
listing_idGhép với listings theo (snapshot_date, listing_id) để lấy neighbourhood_cleansed.
sentimentpositive / neutral / negative. V2: neutral dùng khi có cả khen và chê đáng kể; không ép review thuần thông tin.
aspectsMảng {"aspect": "location", "polarity": "positive"} và các aspect được phép.
languageMã ngôn ngữ như en, hoặc unknown.
statusok, needs_review, error. KPI chỉ xem ok có nhãn hợp lệ là dùng được.
error / splitTruy vết lỗi / dev-test-analysis. KPI TV3 hiện không tự tách KPI theo split hoặc provider.

06

Xử lý lỗi thường gặp

Các trường hợp quan trọng cần hiểu trước khi chạy trên máy mới.

Máy mới clone xong mà báo không có reviews_clean.csv?

Git nhánh TV4 lưu code/config/danh sách ID, không tự tạo bảng QA. Nhận reviews_clean.csv từ TV2 và đặt đúng đường dẫn trong config, hoặc sửa đường dẫn config tới file có thật.

Tại sao --skip-llm báo lỗi dù không gọi API?

Vì nó chỉ đọc file JSONL đã có. Nếu chưa tạo checkpoint v2, không có gì để đọc. Nó không tự tạo kết quả trong chế độ skip.

Tại sao run trả exit code 1 khi vài review đã thành công?

Output bao gồm đủ mẫu, kể cả review chưa gọi API với error=not_attempted. Chỉ cần còn dòng status=error thì CLI trả 1; xem status_counts để phân biệt batch chưa hoàn tất với lỗi HTTP.

Gặp HTTP 429 hoặc timeout có tự retry không?

Không. Code hiện tại ghi checkpoint và dừng ở request lỗi. Kiểm tra quota/key/kết nối rồi chạy lại cùng output để thử tiếp các dòng error; bản ghi hoàn tất được giữ lại.

Vì sao cache khác model, prompt hoặc dữ liệu lại bị từ chối?

Signature hash các cấu hình request, PROMPT và dữ liệu mẫu; API key và tên provider không nằm trong hash. Đổi endpoint/model/prompt/input phải dùng output mới. Không tự sửa signature, không tái dùng kết quả giữa provider khác nhau.

Chạy baseline có dùng API không? Có cần file baseline.py riêng không?

Không. Baseline nằm trong src/llm.py, dựa trên từ khóa và phủ định đơn giản; không gọi API, không cần checkpoint LLM. legacy/src/baseline.py chỉ là lưu trữ code cũ.

Vì sao báo cáo KPI chưa có tỷ lệ dù JSONL có nhãn hợp lệ?

KPI TV3 có ngưỡng mẫu tối thiểu 30 cho một số tỷ lệ. Nếu dưới ngưỡng thì để trống theo thiết kế; cũng cần kiểm tra liệu các dòng status=ok có nhãn hợp lệ và ghép đúng listing hay không.
